## 主笔与适用边界

公众号长文默认直接采用本人开源 `khazix-writer` 的写法。用户已明确卡兹克为首要对标，因此保留原版文章原型、场景开头、私人视角、递进展示、口语转场、低标题密度和结尾回扣。不要抽象成几条通用好文笔原则后自行换一套主笔。

借鉴的是已开源的写作规则。署名、身份、观点归属、产品与亲历均属于当前作者；不把卡兹克写进示例的购买、测试、公司、客户和对话搬到 Andy 身上。不得拼接他人未授权文章作为原创成稿。引用须短、必要、准确并注明归属。

用户当前明确指定的篇幅、受众和交付形式优先；现实事实和身份不能伪造。未指定篇幅时以原版 4000–8000 字为参考，按材料密度决定实际长度。输入是公众号任务时采用本标准，不把这套长文规则强加给 Threads、口播、技术文档或私信。

## 材料与文章原型

动笔前在内部写清五件事，已有上下文能回答就直接采用，不把它变成问卷。

- 谁会读，眼前有什么具体问题。
- 作者想表达的一个主要判断。
- 这次有哪些真实动作、发现、结果或可核实的公开材料。
- 哪一处值得读者继续看，哪一处能提供可执行价值。
- 文章采用什么原型，结尾读者适合做哪一件事。

用原版 HKR 检查选题的趣味或悬念、信息增量、情绪共鸣。材料只支撑其中一项时，先调整切入角度或补研究，不夸大事实制造其他两项。选题评分是编辑判断，不是播放量、阅读量或收入预测。

| 原版文章原型 | 展开方式 | 证据门槛 |
| --- | --- | --- |
| 调查实验型 | 带着问题下场，按过程逐步揭示发现 | 必须有真实调查或实验记录；读到别人的实验只能明确归属地转述 |
| 产品体验型 | 从具体场景入手，让读者跟着操作看结果 | 已验证的操作、输入、输出和限制；官方演示不写成自己的实测 |
| 现象解读型 | 观察引出好奇，研究后形成有依据的判断 | 可核验的现象与来源，相关与因果分开 |
| 工具分享型 | 从真实问题自然引出工具，展示过程与结果 | 项目真实功能、使用条件和实际材料；没有个人故事就从公开事实切入 |
| 方法论分享型 | 围绕经验与案例给出可做的动作 | 每个主要方法有支撑、适用条件、学习成本或常见失败点 |

先按 `human-writing` 的材料门槛核实重要事实。至少五件有出处的具体材料只是长稿的起步检查，不能把五个空泛观点视作五件材料，也不能认为凑够五件就足以支撑八千字。长稿应有多个能展开的阶段、案例或现实关系。

公开材料不足时先检索一手来源和实际项目文件，核对日期、版本、价格、功能与许可证。关键内容只能由用户提供时，最多集中问三个必要问题；用户要求直接出稿时，完成能做的检索后交更窄、更短的可信文章，简述仍缺什么。不要反复提问，也不要虚构亲历填补。

## 初稿的固定要求

**开头碰到事情。** 用具体事件、真实场景、异常事实或正在研究的疑问抓住读者。没有亲历材料时可以从可核验的公开事件起笔；不得添加凌晨几点、注册付费、朋友来电、情绪反应等无来源细节。

**主线只抓一件事。** 每次偏出去补知识、看案例、讲来历，都用自然转场接回当前问题。背景解释只补到读者能继续看，不先铺一段行业概况。知识和判断跟着正在发生的事出来。

**案例逐一展示。** 多个功能、产品或结果按发现感组织，从基础到进阶，再到最有启发的用法。每轮给出新输入、动作、结果或限制，不把同一卖点换三个形容词。只有实际材料证明效果，才能把它放进高潮。

**保留原版声音。** 允许真实的私人判断、承认不知道、自然口语打断、长短句交替和单句成段。不要给口头禅、反问、自嘲和符号设置数量指标，也不要用连续整齐短句制造假节奏。自然表达不是为像作者而编情绪。

**降低标题密度。** 普通叙事长文通常不设正文小标题，靠转场推进。独立方法条目可以编号。用户明确要求目录、教程或标题时按其要求组织，仍保持原版叙事，不套固定「背景—问题—方法—总结」框架。

**结尾接住开头。** 优先回到已展开的事件、问题、物件或判断，让读者感到看完以后理解有所变化。也可采用原版允许的短句留白、行动建议、引用或信念表达。文化、历史和哲学关联必须由前文材料自然引出，不临时拔高，不再摘要一遍全文。

## 两轮审稿与冲突裁决

先由原版 `khazix-writer` 完成四层自检，再用 `human-writing` 的材料规则、非虚构边界和改稿参考做二遍审稿。`human-writing` 在此是编辑，不重新生成初稿，也不加载其通用散文规则来覆盖主笔。

| 冲突或误用 | 本场景处理方式 |
| --- | --- |
| 通用编辑希望删掉「我觉得」「坦率的讲」、口语打断或短段 | 表达有真实作用且不重复就保留；只删机械堆砌，不全面禁用原版声音 |
| 编辑要求压缩，原稿有逐次发现和必要背景 | 删无信息增量的复述，保留让读者理解过程、转折和判断的材料；不按固定比例砍字 |
| 通用规则反对升华、首尾照应 | 保留由事实支撑、确实改变读者理解的回扣和关联；只删空泛拔高及重复总结 |
| 原版「至少若干口语词、单句、自嘲」与材料不相符 | 采用原版检查文件开头的限定，数量是提示，不作硬指标；不为满足配额造经历或情绪 |
| 原版建议「说到底」等过渡，通用规则将其列入翻案外衣 | 不靠单词猜文风。它若在空设误解后抬高论点，改为直接判断；若只是成立的自然转场，不因此重写全段 |
| 用户原话、URL、代码含禁用标点 | 作者正文遵循原版标点；保留 URL、代码、机器字段和专名的准确性；引用不改原意，可改成有归属的转述 |
| 检测器警告某句过短、段落太短、句长变化或情绪词 | 人工回读上下文，警告不能替代文风判断；不得为了检测分数改成均匀段落 |
| 通用写作模块要求加提纲、金句、强转化段或大量标题 | 不执行其默认模板。只有用户明确要求且不损害事实时，才做相应局部调整 |

原版正文硬禁语仍然执行，尤其「说白了」「意味着什么」「这意味着」「本质上」「换句话说」「不可否认」「综上所述」「值得注意的是」「不难发现」和机械「首先、其次、最后」。不要把它们换成同样空泛的新套话。网址、原始文件名和准确来源标题不为扫描分数被篡改。

对 `human-writing/scripts/check_prose.py` 的定位必须准确。它是原版通用散文的检测器，若实际调用，可记录机器命中并逐项判断在本场景的适用性；不能宣称它已验证事实、复刻相似度、阅读体验或爆款概率。没有实际运行就不能写「检测通过」；原版检测未通过而命中项已按本场景裁决保留时，也不能声称原版检测通过。

最后冷读全文，检查读者是否想接着看、作者判断是否有依据、哪个段落还在重复、文章是否已经结束。只修具体问题，避免为修稿而重写整篇。

## 交付形态

| 用户需求 | 默认交付 |
| --- | --- |
| 「写一篇」「按卡兹克风格写」「直接出稿」 | 一个选定标题和完整正文；公开材料支撑的主要结论按需要在文末列关键来源 |
| 「标准化出稿」「完整出稿包」 | 三个标题备选、完整正文 Markdown、真实截图位与说明、关键来源与材料缺口、一个相关行动入口 |
| 「排版」「HTML」「公众号可复制版」 | 在成稿后进入 `MDskill-Web` 排版导出，核实导出物；保留可编辑原稿 |
| 「只改稿」「只审稿」 | 按明确范围编辑或审查；不额外扩写全文或添加营销段 |

标准出稿包里，三个标题分别突出可信结果、具体好奇点、读者收益，但不能写大于材料的承诺。正文内不展示内部提纲、HKR 评分、规则检查、测试记录和制作过程。来源表、素材缺口和配图清单与正文分开，便于用户直接复制成稿。

## 截图、来源与行动入口

只放确实能证明当前段落的真实截图。每个截图位写明要拍的界面、输入或操作、关键结果和一行说明。没有素材时在正文外标记「待补真实截图」，不要生成仿造产品结果、收益截图、用户对话或测试成绩。用户只要正文时，不因缺少非必需配图而阻塞出稿。

核验事实时保留来源 URL、日期和支持的具体主张；来源不能只证明项目存在，却被用来证明作者已经使用成功。个人经历来自用户明确提供或已确认可公开的材料。未确认的客户信息、私聊、财务与家庭信息不能作为写作素材。

文章讲 Andy 的项目时，核对实际仓库、网站、功能、免费范围与运行成本，再设计一个与本文结果直接相关的行动入口。优先让读者打开对应项目、照步骤试一次或获取当前材料。没有更合适的项目入口且确有介绍作者的需要时，可使用公开主页 [AIPMAndy](https://github.com/AIPMAndy) 或 [AI 酋长 Andy](https://metaver.vip/)；两者不同时硬塞进文章。不要编造微信号、二维码、价格、服务承诺、粉丝增长或客户结果。

## 排版与完成状态

`MDskill-Web` 是现有排版出口的路由，读取项目当前说明并确认当前工具是否可调用，再进行实际操作。本标准没有内置它的运行环境、公众号账号连接或自动发布能力。

- 只生成 Markdown，就报告已完成原稿。
- 已执行导出并读回 HTML 文件，才报告已导出 HTML。
- 截图位置已规划，就报告待补真实截图，不能写已完成配图。
- 实测、文件检查、预览验收分别记录实际发生的结果，不用「规则已配置」替代「流程已跑通」。
- 发布属于另外的明确任务；没有真实执行及结果证据，不能声称已发布公众号。

用户只问文章时，不向正文添加技术路径、安装步骤、审核分数或工具状态。只有交付确实受阻，才简短解释具体缺口，并继续完成其余已授权部分。
