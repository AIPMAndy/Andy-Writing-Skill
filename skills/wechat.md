# 场景：微信公众号长文，以卡兹克原版为主笔

将「数字生命卡兹克」作为此场景的首要写作对标。采用其本人开源的 `khazix-writer` 作为唯一主笔，具体文章仍以 Andy 或用户指定的真实作者为叙述者。不要改成泛泛的「Andy 风格」，不要把多个写作 Skill 的模板叠在一起。

## 读取与分工

先读取 [公众号出稿标准](../references/wechat-standard.md)，再按阶段读取原版材料。

| 阶段 | 使用文件 | 职责 |
| --- | --- | --- |
| 定选题、写初稿 | [khazix-writer 原版](../vendor/khazix-writer/SKILL.md) 与 [风格示例](../vendor/khazix-writer/references/style_examples.md) | 决定文章原型、开头、主线、节奏、自然转场和结尾 |
| 选题不清或案例设计 | [内容方法论](../vendor/khazix-writer/references/content_methodology.md) | 判断 HKR、选择切入点、组织递进展示 |
| 材料与事实 | [human-writing 入口的材料规则](../vendor/human-writing/SKILL.md) 与 [非虚构边界](../vendor/human-writing/references/reality.md) | 核实公开事实、来源、数字、亲历和因果；不接管初稿文风 |
| 初稿自检 | [khazix-writer 四层检查](../vendor/khazix-writer/references/quality-check.md) | 检查硬规则、风格一致性、内容质量和真人表达 |
| 二遍审稿 | [human-writing 改稿参考](../vendor/human-writing/references/revision.md) | 只修缺证据、重复解释、空话、机械套话和指代不清；按出稿标准裁决冲突 |
| 排版导出 | `MDskill-Web` | 仅在用户要求排版或 HTML 时调用，并核实是否实际完成 |

不要自动串联 `wechat-explosive-article-skill`、`GaoMiDuSkill`、通用 `humanizer` 或营销文案模块再重写一遍。它们不能覆盖本场景的主笔；用户点名要求时只执行指定的局部任务。

## 执行顺序

1. **定一篇文章的任务。** 从用户材料中确定读者、一个核心判断、读完能获得的具体价值和文章原型。信息足够直接写，不要求用户先填表。
2. **查材料。** 把用户明确提供的经历、可核验的公开事实、作者推断和未知分开。材料不足先检索；只有用户掌握的关键经历确实缺失时才集中追问。用户要求直接写时，先完成可做的研究，再缩小范围或缩短篇幅。
3. **按原版写。** 默认参考 4000–8000 字，用户明确篇幅优先。采用具体事件或场景开头、发现的逐次递进、自然转场、长短句与段落的变化、收尾回扣。不要用假亲历、重复观点或空泛升华撑长度。
4. **完成两轮审稿。** 先按原版四层检查修稿，再由 `human-writing` 做受限的二遍编辑。保留成立的停顿、口语打断、短段落、递进案例和尾部回扣；不要把全文压成提纲、报告或统一的短句。
5. **按请求交付。** 用户只要文章，优先交标题和正文，必要来源简列文末。要求标准出稿包时，再提供标题备选、正文 Markdown、真实截图位、来源与材料缺口、相关行动入口；要求 HTML 时再进入排版导出。

## 交稿前必查

- 开头确有可追溯的事、观察或疑问；第一人称动作确实属于作者。
- 每个主要段落增加事实、动作、例子、判断或必要情绪，主线读得顺。
- 保留卡兹克原版的叙事和节奏，不把「去 AI 味」做成抹平文风。
- 全文不用「说白了」「意味着什么」「这意味着」「本质上」「换句话说」「不可否认」及原版列明的其他套话；同义替换也不能继续空转。
- 正文标点遵循原版。网址、代码、产品名和机器字段保持准确，不为清标点损坏它们。
- 文章事实、截图、运行结果和已发布状态各有相应证据；规则文件和占位符不能充当实测证据。
- 只有与读者下一步行动直接相关时，才保留一个 Andy 项目或服务入口。不强塞多个链接或无关销售段。
